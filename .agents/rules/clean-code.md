# 🧼 Clean Code & Engineering Standards (Liman Web API)

Все AI-агенты, работающие над проектом **liman-web-api**, обязаны строго следовать настоящим стандартам проектирования и написания кода, основанным на практиках **Роберта Мартина (Uncle Bob)**, **Мартина Фаулера** и принципах **SOLID, DRY, KISS**.

---

## 1. DRY (Don't Repeat Yourself)

1. **Никакой нумерованной копипасты (Numbered Slots / Columns):**
   - ❌ **Запрещено:** Создавать цепочки переменных вида `const p1 = ...; const p2 = ...;` и дублировать проверки `if (p1) ... if (p2) ...`.
   - ✅ **Обязательно:** Описывать слоты в виде типизированного кортежа/массива констант (например, `NAMEDESC_PHOTO_COLUMNS = ['photo', 'photo2', ...] as const`) и обрабатывать их через функциональные пайплайны (`map`, `forEach`, `filter`).
2. **Единая точка синхронизации зависимых таблиц (Zero Branch Duplication):**
   - ❌ **Запрещено:** Дублировать сопутствующие операции (сохранение остатков, медиа, штрихкодов) внутри веток `if (isUpdate) { ... } else { ... }`.
   - ✅ **Обязательно:** В ветках `if/else` выполнять исключительно специфичные для ветки действия (например, `UPDATE name2` vs `INSERT name2`), а всю общую логику обновления связанных сущностей выносить в единую функцию (например, `syncProductRelations(...)`).
3. **DRY в SQL-запросах:**
   - Формирование списков колонок и плейсхолдеров для динамических вставок должно строиться декларативно из метаданных колонок, а не копироваться вручную.

---

## 2. SOLID Principles

1. **SRP (Single Responsibility Principle) & SLAP (Single Level of Abstraction):**
   - Каждая функция должна делать ровно одну вещь на одном уровне абстракции.
   - Метод-координатор (например, `upsertProductFromExternal`) управляет только транзакционными границами и оркестрацией шагов. Вся конкретная работа делегируется специализированным приватным методам (`resolveExistingProductTcod`, `updateProductMaster`, `insertProductMaster`, `syncProductRelations`).
2. **OCP (Open/Closed Principle):**
   - Поведение системы должно расширяться без модификации уже проверенных базовых вычислений (использование конфигураций колонок, мапперов платформ).
3. **DIP (Dependency Inversion):**
   - Зависимости внедряются через NestJS DI (`constructor`).
   - Операции с базой данных в транзакциях принимают абстрактный интерфейс исполнителя запросов (`conn: mysql.Pool | mysql.PoolConnection`), что облегчает мокирование и тестирование.

---

## 3. Clean Code (Robert C. Martin - Uncle Bob)

1. **Искоренение Magic Numbers & Strings:**
   - ❌ **Запрещено:** Использовать «магические числа» в коде (`substring(0, 100)`, `substring(0, 14)`, `retries = 3`).
   - ✅ **Обязательно:** Все системные лимиты MariaDB, имена колонок и параметры повторов объявлять в именованных константах предметной области (например, `LIMAN_LIMITS.NAME_MAX_LEN`, `LIMAN_LIMITS.MAX_TCOD_INSERT_RETRIES`).
2. **Осмысленные имена (Intention-Revealing Names):**
   - Никаких сокращений вида `p1`, `d`, `c`, `tmp`. Переменная должна говорить, что она хранит (`photoSlots`, `descBuffer`, `truncatedName`, `priceCol`).
3. **Command-Query Separation (CQS):**
   - Функции поиска (`resolveExistingProductTcod`, `findProductBySkuOrBarcode`) не должны менять состояние БД.
   - Функции мутации (`updateProductMaster`, `insertProductMaster`, `saveNamedescMedia`) должны четко отвечать за запись.

---

## 4. Enterprise Patterns & Robustness (Martin Fowler)

1. **Строгие транзакционные границы (Atomic Transactions):**
   - Любая операция, затрагивающая более одной таблицы (`name2`, `name2ost`, `namedesc`, `strihcod`), **обязана** выполняться в единой транзакции:
     ```typescript
     const conn = await pool.getConnection();
     try {
       await conn.beginTransaction();
       // ... атомарные шаги ...
       await conn.commit();
     } catch (err) {
       await conn.rollback();
       throw err;
     } finally {
       conn.release();
     }
     ```
2. **Защита от Race Conditions при параллельном импорте:**
   - При генерации первичных ключей `MAX(tcod)+1` обязательно использовать блокировку строк `FOR UPDATE`.
   - Вставку оборачивать в цикл с ретраями на случай коллизии `ER_DUP_ENTRY` с логированием предупреждения.
3. **Ограничение потребления ресурсов и памяти (Resource Caps):**
   - Все пакетные операции должны иметь жесткие лимиты на размер отчетов в памяти (например, `MAX_REPORT_ITEMS = 200` с флагом `itemsTruncated`).
   - Долгие операции выгрузки/импорта должны делегироваться в очереди BullMQ с возвратом `202 Accepted` и отслеживанием статуса, исключая HTTP Gateway Timeout (504).

## 5. Обязательный чеклист перед сдачей кода

Каждый агент перед завершением задачи обязан:
- [ ] Проверить отсутствие дублирования логики и нумерованных переменных (`p1`, `p2`, ...).
- [ ] Проверить, что длина методов не превышает 30-40 строк и соблюдается SRP.
- [ ] Убедиться в отсутствии магических чисел и литералов.
- [ ] Проверить корректность транзакций и гарантированный `conn.release()` в блоке `finally`.
- [ ] Запустить и убедиться в 100% успехе тестов: `npm test`.
- [ ] Запустить и подтвердить компиляцию TypeScript: `npm run build`.
