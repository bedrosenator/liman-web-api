# 🤖 Agent Rules (Liman Web API)

## 🚨 Обязательные правила для всех AI-ассистентов и агентов

### 1. Git Workflow & Deployment
* **ВСЕГДА СОЗДАЕМ PULL REQUEST ПЕРЕД ДЕПЛОЕМ!**
* Запрещен прямой коммит/пуш в `main` или запуск деплоя без предварительно оформленного Pull Request.
* Любые изменения разрабатываются в отдельной ветке (`feat/...`, `fix/...`), тестируются, пушатся в GitHub и оформляются в PR со ссылкой для ревью.
* Деплой на сервер запускается только после ревью и мерджа PR в `main`.

### 2. Чистый код и универсальность (Multi-tenancy)
* Никакого хардкода конкретной предметной области в кодовой базе (например, табачной продукции, электроники, одежды). Система обслуживает разных клиентов из разных доменов.
* Соблюдение SOLID, DRY, KISS. Отсутствие дублирования кода.
* 100% прохождение всех unit-тестов перед каждым коммитом.

### 3. Декомпозиция файлов и ограничения на размер
* **Максимальный размер файла: 300 строк** для компонентов (`*.tsx`, `*.ts`), 500 строк для сервисов NestJS. Файлы, превышающие лимит, **обязательно** разбиваются на части.
* Каждый компонент решает ровно одну задачу (Single Responsibility). Файл-«оркестратор» (например, `PromTab.tsx`) должен содержать только state-логику и компоновку — весь JSX-блок выносится в дочерние компоненты.
* **Правило именования подпапок**: если для фичи нужно более 2 файлов — создаётся подпапка `<feature>/`:
  ```
  src/components/portal/prom/
  ├── PromTab.tsx            # оркестратор (state + layout, ≤150 строк)
  ├── PromHealthGrid.tsx     # блок статусов / «светофор»
  ├── PromActionHub.tsx      # карточки действий
  ├── PromFeedCard.tsx       # YML-фид
  └── PromSettingsForm.tsx   # форма настроек API
  ```
* Строки вне i18n запрещены: все пользовательские строки — через `t('key')` из `translations.ts`. Никаких `language === 'uk' ? '...' : '...'` инлайн в JSX.
* `tenant: any` и аналогичные широкие типы запрещены — всегда объявляется конкретный интерфейс/тип.

### 4. Честные статусы синхронизаций и специфика маркетплейсов
* **Никаких ложных success**: запрещено возвращать статус `success` и зелёные галочки, если обновлено или создано `0` товаров при наличии позиций в базе. При `0` товаров выставляется статус `warning` с внятным объяснением и указанием шагов для пользователя (например, необходимость загрузки YML-фида в кабинете продавца).
* **Связи `product_mappings`**: сохраняются со статусом `synced` **только** для тех артикулов, которые внешний API реально подтвердил в `processed_ids`.
* **Специфика Prom.ua**: создание новых карточек через JSON REST API невозможно (только через YML-фид); пакетное обновление существующих товаров по внешнему коду выполняется через `POST /products/edit_by_external_id` (с полем `id: string`).
