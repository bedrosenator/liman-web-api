# 🤖 Agent Rules (Liman Web API)

## 🚨 Обязательные правила для всех AI-ассистентов и агентов

### 1. Планирование и согласование (Plan-First Approach)
* **ВСЕГДА СОЗДАЕМ И ОБСУЖДАЕМ ПЛАН РЕАЛИЗАЦИИ ДО НАЧАЛА КОДИРОВАНИЯ!**
* Запрещено приступать к написанию или изменению кода без предварительного составления плана и его явного согласования с пользователем.
* Порядок действий агента:
  1. **Анализ**: исследовать существующую кодовую базу, контракты API и предметную область.
  2. **План**: составить чёткий пошаговый план (затрагиваемые файлы, архитектурные решения, изменения в БД/API/UI, стратегия тестирования).
  3. **Обсуждение**: представить план пользователю, подсветить потенциальные риски и альтернативы, дождаться одобрения/корректировок.
  4. **Реализация**: приступать к кодированию строго после подтверждения плана пользователем.

### 2. Git Workflow & Deployment
* **ВСЕГДА СОЗДАЕМ PULL REQUEST ПЕРЕД ДЕПЛОЕМ!**
* Запрещен прямой коммит/пуш в `main` или запуск деплоя без предварительно оформленного Pull Request.
* Любые изменения разрабатываются в отдельной ветке (`feat/...`, `fix/...`), тестируются, пушатся в GitHub и оформляются в PR со ссылкой для ревью.
* Деплой на сервер запускается только после ревью и мерджа PR в `main`.

### 3. Чистый код и универсальность (Multi-tenancy)
* Никакого хардкода конкретной предметной области в кодовой базе (например, табачной продукции, электроники, одежды). Система обслуживает разных клиентов из разных доменов.
* **Запрещён хардкод «магических строк» (magic strings)**: статусы процессов, очередей, интеграций и модалок (`idle`, `running`, `completed`, `error` и др.) строго выносятся в типизированные словари-константы (`as const`) или `enum`. Запрещено писать `status === 'completed'` напрямую в JSX или редьюсерах.
* Соблюдение SOLID, DRY, KISS. Отсутствие дублирования кода.
* 100% прохождение всех unit-тестов перед каждым коммитом.

### 4. Декомпозиция файлов и ограничения на размер
* **Максимальный размер файла: 300 строк** для компонентов (`*.tsx`, `*.ts`), 500 строк для сервисов NestJS. Файлы, превышающие лимит, **обязательно** разбиваются на части.
* Каждый компонент решает ровно одну задачу (Single Responsibility). Файл-«оркестратор» (например, `PromTab.tsx`) должен содержать только state-логику и компоновку — весь JSX-блок выносится в дочерние компоненты.
* **Правило именования подпапок**: если для фичи нужно более 2 файлов — создаётся подпапка `<feature>/`:
  ```
  src/components/portal/prom/
  ├── PromTab.tsx            # оркестратор (state + layout, ≤150 строк)
  ├── PromHealthGrid.tsx     # блок статусов / «светофор»
  ├── PromActionHub.tsx      # карточки действий
  ├── PromFeedCard.tsx       # YML-фид
  └── PromSettingsForm.tsx   # форма настроек API
  ```
* Строки вне i18n запрещены: все пользовательские строки — через `t('key')` из `translations.ts`. Никаких `language === 'uk' ? '...' : '...'` инлайн в JSX.
* `tenant: any` и аналогичные широкие типы запрещены — всегда объявляется конкретный интерфейс/тип.

### 5. Честные статусы синхронизаций и специфика маркетплейсов
* **Никаких ложных success**: запрещено возвращать статус `success` и зелёные галочки, если обновлено или создано `0` товаров при наличии позиций в базе. При `0` товаров выставляется статус `warning` с внятным объяснением и указанием шагов для пользователя (например, необходимость загрузки YML-фида в кабинете продавца).
* **Связи `product_mappings`**: сохраняются со статусом `synced` **только** для тех артикулов, которые внешний API реально подтвердил в `processed_ids`.
* **Специфика Prom.ua**: создание новых карточек через JSON REST API невозможно (только через YML-фид); пакетное обновление существующих товаров по внешнему коду выполняется через `POST /products/edit_by_external_id` (с полем `id: string`).

### 6. Безупречный UI: правила верстки, изоляция границ и отсутствие артефактов (TASK-40)
* **Никаких вылезаний за границы**: все flex-контейнеры и элементы с текстом переменной длины (URL фида, токены, названия магазинов) обязаны иметь `min-w-0` для корректной работы `truncate`.
* **Компактные индикаторы (`HealthGrid`)**: кнопки действий внутри карточек здоровья (проверка связи, refresh) оформляются строго как `.btn-icon.btn-icon--sm` со спиннером и всплывающей подсказкой `title`, а не длинным текстом, выталкивающим элемент за границы карточки 280-320px. Сама карточка `.health-card` должна иметь `min-width: 0; overflow: hidden;`.
* **Сброс нативных стилей кнопок**: при использовании тега `<button>` в качестве заголовка или аккордеона (`card__header`), обязательно сбрасывать нативные стили (`bg-transparent border-0 outline-none w-full text-left`), чтобы браузер не рендерил дефолтный серый бордер и фон.
* **Аккордеоны**: в свёрнутом состоянии (`isOpen === false`) отключать `border-bottom` у заголовка (`.card__header`), чтобы не образовывался двойной бордер на дне пустой карточки.
* **Бейджи статусов**: `.badge--subtle`, `.badge--emerald` и др. не должны иметь собственных внешних рамок (`border: none`), чтобы не создавать визуального шума («бордер внутри бордера») при размещении внутри кнопок `.btn--secondary`.
* **Табы каналов**: таб-бар на pill-кнопках (`btn btn--sm`) не должен иметь под собой оторванных полос-разделителей (`border-b border-subtle pb-3`).
* **Модальные экраны завершения (`ExportCompletedScreen`, `ImportCompletedScreen`)**: иконки статусов (`AlertTriangle`, `CheckCircle2`) обязательно оформлять в бейджи со свечением `.warning-badge-glow` и `.success-badge-glow` с центровкой `margin: 0 auto; display: flex; align-items: center; justify-content: center;`. Между иконкой, заголовком (`mb-2`), описанием (`mb-6`) и сеткой карточек (`mb-5`) соблюдать четкие отступы, не допуская сжатия текста и слипания с карточками.
